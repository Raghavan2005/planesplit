# Agent Verification & Critique Notes

This document contains the critiques generated by the Reliability and Judge agents after reviewing the initial plan. These points **must be addressed** before implementation begins.

## 1. Network Reliability Critique (Theoretical Flaws)
* **The "God View" Flaw:** Our initial architecture assumed instantaneous Control Plane (RIB) updates across all nodes. This ignores real-world CP propagation delays. *Resolution:* The implementation should account for CP propagation time, or explicitly document this abstraction.
* **Test Coverage Limit (Active Probing):** Randomly probing a single IP within a subnet is insufficient. A partial rule application (e.g., `/25` instead of `/24`) might be missed depending on the randomly selected IP. *Resolution:* The prober must use boundary analysis (Header Space Analysis concepts) to strategically pick IPs that test the edges of subnet rules.
* **Wall-Clock vs Discrete Time:** Relying on `time.sleep()` for the grace window causes flaky, non-deterministic tests. *Resolution:* Use a Discrete Event Simulation (DES) approach where time is manually "stepped" forward in ticks.

## 2. Hackathon Judge Critique (Demo Weaknesses)
* **Missing Dramatic Consequences:** A packet simply dropping is a weak visual. *Resolution:* The demo must showcase a **Routing Loop** (e.g., A -> B -> C -> B -> C...) to visually prove the practical consequence of a data-plane mismatch.
* **Black-Box Demo:** A fully automated script can be perceived as "smoke and mirrors" or hardcoded by judges. *Resolution:* The CLI must be interactive. Allow the judge to input the delay duration or manually trigger the fault injection.
* **Missing Edge Cases in Demo:** The original demo plan skipped the most complex fault (rule corruption). *Resolution:* Ensure the demo includes injecting a corrupted rule (e.g., `/25`) to prove the system doesn't just diff configuration strings, but actually mathematically simulates the forwarding.
